## 测试说明

1. **测试目标**：验证系统在非标准自然语言表达方式下的鲁棒性
2. **判断标准**：成功生成正确的筛选条件和分析计划，最终能查询到正确数据即为通过
3. **预期结果**：原始标准query通过率 ≈ 100%，多样化query通过率越高，系统鲁棒性越好

## 🎯 预测试分析与结果预测

基于现有系统能力分析（原e2e 8个标准query都能通过），预测各query测试结果：

**现有系统能力边界：**
- ✓ 标准结构：`[实体ID] [月份] 的 [指标] [分析类型]` → 能正确解析
- ✓ 层级明确：明确说"广告主"、"广告计划" → 能正确识别目标层级
- ✓ 关键词清晰：明确说"趋势"、"对比"、"分布"、"列表" → 能正确识别分析类型
- ✓ 单一条件：一个筛选条件 + 一个分析需求 → 能处理
- ✗ 名称匹配/模糊筛选：系统训练/提示中很少有按名称筛选的案例
- ✗ 多条件组合：where筛选（名称）+ having筛选（指标）两步混合，容易错
- ✗ 口语化省略：省略关键词，只说名称 → 意图理解容易错
- ✗ 表述倒装/换序：把条件放后面 → 实体提取可能错
- ✗ 模糊包含："名称包含mini"这种模糊匹配，生成ES筛选条件容易错

## 🧐 深度失败原因分析

### 各失败原因详细拆解

#### 1. 🐛 **意图识别不提取advertiser_id（核心问题 - 24次失败）**

**现象**：
用户提供了广告主名称（如 `digital_0`），意图识别阶段正确理解了需求、正确识别了metrics和time_range，但就是 **不提取advertiser_ids，始终留空**：

```python
# 输出示例（测试 case 1）
{
  "advertiser_ids": [],  # ❌ 空数组！
  "campaign_ids": [],
  "ad_group_ids": [],
  "creative_ids": [],
  "metrics": ["cost"],
  ...
}
```

进入CoT分析阶段，发现 `advertiser_ids` 为空 → 触发 "找不到广告主" → 要求用户澄清。

**覆盖案例**：所有按名称查询的case都中枪：
- 测试 1-4, 6-10, 12, 15, 18-22, 55-60 → **共24次**，占所有失败的 **60%**

**根因分析**：
意图识别prompt中 **缺少按名称查询的few-shot案例**。系统只见过用户给ID的情况，不知道拿到名称后应该怎么处理 → 不敢推断，选择安全选项（要求澄清）。

---

#### 2. 🐛 **索引名称不一致（1次失败）**

**现象**：
测试51 (`广告主6四月份点击量超过100的创意有哪些`)，需要从 `advertiser` → `ad_group` → `creative` 层级下钻。
- LLM生成索引名 `ad_group`（带下划线）
- 但ES中实际索引名是 `adgroup`（无下划线）
- → 直接抛出：
```
NotFoundError(404, 'index_not_found_exception', 'no such index [ad_group]', ad_group, index_or_alias)
```

**根因**：代码中索引名称映射与ES实际不一致，简单字符串错误。

---

#### 3. 🐛 **操作符词汇不匹配（1次失败）**

**现象**：
测试17 (`digital_0 中名称包含 summer 而且四月份消耗大于100的广告计划有哪些`)，对于"名称包含"：
- LLM根据通用SQL知识习惯生成：`"operator": "like"`
- 但系统验证层只允许 `contains`，不接受 `like`
- → 直接验证错误失败

**根因**：prompt中没有明确强调说明"包含"必须使用 `contains` 操作符，导致词汇不匹配。

---

#### 4. 🐛 **分析类型选择错误（2次失败）**

**现象**：
- 测试11 (`digital_0 下 精选六一八0 这个广告组四月份消耗是多少`)
- 测试13 (`digital_0 的广告组 mini_045 四月份点击率是多少`)

用户明确要求查询 **具体实体** 的数据，应该选择 `entity_table`，但LLM错误选择了 `summary` → 结果类型不匹配被判失败。

**根因**：CoT prompt中对 `entity_table` vs `summary` 的区分规则不够清晰 → LLM容易混淆。

---

#### 5. 🐛 **分析结构正确但结果为空（12次失败）**

**现象**：
测试14、16、31-39、49-50、52 → 共12次。
- 分析类型选择正确 ✓
- 筛选计划结构正确 ✓
- 但执行DSL查询后返回空结果 → 被判失败

**重新验证ES真实数据后结论**：

| 测试ID范围 | 数量 | 结论 |
|------------|------|------|
| 31-33 (列出未删除campaign) | 3 | 🐛 **应该返回11行数据**（11个campaign都存在）→ 系统bug |
| 34-36 (消耗 > 10) | 3 | 🐛 **应该返回2行数据**（campaign 13=17750, campaign 12=1373，都满足>10）→ 系统bug |
| 37-39 (广告主层级entity_table) | 3 | 🐛 **应该返回1行数据**（广告主本身存在，四个指标都有值）→ 系统bug |
| 49-50 (adgroup TopN) | 2 | 🐛 **应该返回TopN结果**（所有adgroup都有消耗/点击率数据）→ 系统bug |
| 52 (creative TopN) | 1 | 🐛 **应该返回TopN结果**（所有creative都有转化率数据）→ 系统bug |
| 14, 16 (三层名称查询特定creative) | 2 | 🔴 还是那个核心问题：意图识别提取不了advertiser_ids → 空查询结果 |

**数据验证**（ES真实查询结果）：
```
campaign_id | 文档数 | 总消耗
-----------|--------|-------
         13 |    346 | 17750.00
         12 |     23 |  1373.00
-------------------------------
  总计:            19123.00
```

所以确实有数据，**这12个返回空全部都是系统bug，不是数据问题**。

#### 6. ✅ **极度模糊query合理澄清（4次）**

**现象**：
测试56 (`digital_0`)、57 (`digital_0四月`)、58 (`给我看看digital_0最近数据`)、59 (`六号广告主最近表现怎么样`) → 共4次。

用户提供信息确实不完整：
- 缺少具体分析需求
- 缺少metrics列表
- 缺少明确时间范围

系统要求澄清 **完全正确**，这不是bug，是合理的安全设计，应该保留当前行为。
