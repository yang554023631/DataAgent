# 意图识别模块优化设计文档

> 日期：2026-08-05
> 状态：待评审
> 对应分支：insight-engine-optimization-0804

## 1. 背景与目标

### 1.1 现状问题

当前意图识别模块存在以下不足：

1. **纯规则二分类，准确率有限**：`IntentRouter` 仅基于关键词做 `report` / `knowledge` 二分类，无法处理自然语言表达和边界模糊的问题
2. **无拒答能力**：领域外问题（如"今天天气怎么样"）误走 RAG 流程，最终只能说"知识库中没有找到"，体验差
3. **NLU 解析能力弱**：纯规则的指标/维度/时间解析，对复杂句式、口语化表达、别名歧义的处理能力不足
4. **澄清机制单一**：HITL 仅用于广告主歧义，缺少通用的需求澄清能力
5. **无能力校验**：用户提出超出系统支持范围的查询时，没有前置校验和引导

### 1.2 优化目标

1. **引入 LLM 增强意图识别**，从纯规则升级为"规则快筛 + LLM 精分"的混合方案
2. **支持三分类 + 拒答**：报表查询 / 知识问答 / 领域外（拒答）
3. **分层识别架构**：顶层分类 + 第二层专项识别，每层独立可演进
4. **通用澄清机制**：低置信度、信息缺失、能力不支持时，走 HITL 澄清
5. **回退机制**：第二层澄清时用户意图变化，可回退到第一层重新分类
6. **降低幻觉**：信息不足时追问，不明确时澄清，领域外时拒绝

## 2. 总体架构

### 2.1 分层架构

```
用户输入
   │
   ▼
┌─────────────────────────────────────────┐
│  Layer 1: 顶层意图分类器                  │
│  ─────────────────────────              │
│  - 规则快筛（关键词匹配，毫秒级）          │
│  - LLM 精分（三分类 + 置信度）            │
│  - 输出：category, confidence, reason    │
└───────────────┬─────────────────────────┘
                │
    ┌───────────┼───────────┐
    ▼           ▼           ▼
 ┌───────┐  ┌──────────┐  ┌──────┐
 │ 报表  │  │ 知识问答  │  │ 拒答 │
 │  流程 │  │   流程    │  │ 结束 │
 └───┬───┘  └─────┬────┘  └──────┘
     │            │
     ▼            ▼
┌─────────┐  ┌──────────┐
│ Layer 2 │  │ Layer 2  │
│ 报表意图 │  │ 知识意图  │
│ 识别填充 │  │ 识别填充  │
│ + 澄清  │  │ + 澄清   │
└────┬────┘  └─────┬────┘
     │             │
     ▼             ▼
  报表流程      RAG 流程
```

### 2.2 循环与回退机制

- **回退触发条件**：第二层澄清时，用户补充的内容表明意图类别发生变化（如知识问答澄清时用户说"我其实是想查数据"）
- **回退计数**：只有"第二层 → 第一层"的回退算一次循环，层内澄清不计入
- **最大循环次数**：3 次
- **超限处理**：3 次后全量重置 state，提示用户重新提问，忽略之前的对话

### 2.3 现有流程对比

| 阶段 | 当前 | 优化后 |
|------|------|--------|
| 入口 | `intent_router`（关键词二分类） | `intent_classifier`（规则快筛 + LLM 三分类 + 置信度） |
| 报表解析 | `nlu_node`（纯规则） | `report_intent_node`（LLM + 规则混合 + 能力校验 + 澄清） |
| 知识问答 | 直接走 RAG | `knowledge_intent_node`（分类 + 主题提取 + 范围引导） |
| 领域外 | 误走 RAG → 兜底回答 | `reject_node` → 明确拒答 |
| 澄清 | 仅广告主歧义 | 通用澄清（意图不明 / 缺信息 / 能力不支持 / 别名歧义） |
| 回退 | 无 | 第二层澄清时意图变化可回退第一层 |

## 3. Layer 1：顶层意图分类器

### 3.1 职责

判断用户输入属于哪一类：`report` / `knowledge` / `out_of_domain`，并输出置信度。

### 3.2 混合策略：规则快筛 + LLM 精分

#### 3.2.1 规则快筛（快速路径）

**只做一件事：快速放行明确的报表查询。**

判定逻辑（满足以下任一条即走报表快速路径）：

- 同时命中"时间词" + "指标词"（如"昨天的曝光"）
- 命中"报表查询动作词" + "广告相关词"（如"查看 消耗"、"查询 CTR"）
- 命中明确的对比模式（如"3月 vs 4月"、"本周和上周"）

快速路径下，直接输出 `category=report, confidence=1.0, source=rule_fastpath`，跳过 LLM 调用。

**规则快筛不做的事：**
- 不做"确定是知识"的判断（宁可让 LLM 裁决，避免误杀）
- 不做"确定是领域外"的判断

#### 3.2.2 LLM 精分

规则快筛未命中的所有请求，走 LLM 分类。

**LLM 输入：**
- 用户输入（`user_input`）
- 对话历史（`conversation_history`，最近 5 轮）
- 分类体系说明（报表 / 知识 / 领域外 的定义和边界）

**LLM 输出（JSON）：**
```json
{
  "category": "report | knowledge | out_of_domain",
  "confidence": 0.0,
  "reason": "简要判断依据，用于日志调试"
}
```

**置信度阈值：**
- `confidence >= 0.7` → 高置信度，按分类结果路由
- `confidence < 0.7` → 低置信度，触发意图澄清 HITL

### 3.3 状态字段（State）

新增/修改的 state 字段：

```python
# 顶层分类结果
intent_category: str               # "report" | "knowledge" | "out_of_domain"
intent_confidence: float           # 0.0 ~ 1.0
intent_classify_source: str        # "rule_fastpath" | "llm"
intent_reason: str                 # 判断依据（日志用）

# 回退计数
reentry_count: int                 # 回退到第一层的次数，默认 0

# 澄清状态
clarification_type: str            # "intent_confirm" | "missing_info" | ...
clarification_question: str        # 向用户澄清的问题
clarification_options: list        # 澄清选项（可选）
```

## 4. Layer 2-报表：报表意图识别与填充

### 4.1 职责

从用户自然语言中提取报表查询所需的结构化信息，做能力校验，必要时触发澄清。

### 4.2 必填字段（缺了就澄清）

| 字段 | 说明 | 示例 |
|------|------|------|
| `advertiser_ids` | 广告主 ID 列表 | `[123]` |
| `time_range` | 时间范围 | `{start_date, end_date, unit}` |
| `metrics` | 指标列表 | `["impressions", "clicks", "ctr"]` |
| `ad_level` | 广告层级 | `"campaign" | "ad_group" | "creative"` |

**可选字段：**
- `group_by`：细分维度（性别、年龄、地区等）
- `filters`：过滤条件
- `is_comparison`：是否对比查询
- `compare_time_range`：对比时间范围
- `chart_type`：期望的图表类型
- `top_n`：Top N 限制

### 4.3 支持的能力清单（用于校验）

**指标（9 个）：**
`impressions`（曝光）、`clicks`（点击）、`cost`（消耗）、`conversions`（转化）、`reach`（覆盖）、`frequency`（频次）、`ctr`（点击率）、`cvr`（转化率）、`roi`（投产比）

**广告层级（3 个）：**
`campaign`（计划）、`ad_group`（广告组）、`creative`（素材/创意）

**维度（17 个）：**
- 时间维度：`data_date`、`data_hour`、`data_month`、`data_week`
- 业务维度：`campaign_id`、`adgroup_id`、`creative_id`、`industry`、`region_id`、`device_type`
- 受众维度：`audience_gender`、`audience_age`、`audience_os`、`audience_os_version`、`audience_country`、`audience_city`、`audience_interest`

**时间范围：**
- 相对时间：今天、昨天、近 N 天 / N 周 / N 月、本周、上周、本月、上个月
- 绝对时间：指定日期范围、指定月份
- 生命周期：某广告对象的投放生命周期（需先查询首次投放日期）
  - 实现方式：报表意图识别层解析出"生命周期"需求后，根据已识别的广告层级和广告对象，
    查询该对象的首次投放日期，计算完整时间范围后填充到 `time_range` 字段
  - 若无法确定广告对象或查不到首次投放日期 → 触发澄清

### 4.4 解析策略：LLM 主解析 + 规则工具校验

**流程：**

```
用户输入 + 对话历史
   │
   ▼
┌─────────────────────┐
│ LLM 结构化解析       │  ← 一次调用输出所有字段
│ 输出完整 query_intent │
└──────────┬──────────┘
           │
   ┌───────┴───────┐
   ▼               ▼
规则工具校验     能力校验
（time_parser,   （指标/层级/维度/时间范围
 map_metrics,     是否在支持范围内）
 map_dimensions）
   │               │
   └───────┬───────┘
           │
   ┌───────┴───────┐
   │ 一致性检查     │
   │ LLM vs 规则   │
   └───┬───────┬───┘
       ▼       ▼
    一致     不一致
     │        │
     │        ├─ 置信度高的为准
     │        └─ 都拿不准 → 触发澄清
     │
     ▼
  必填字段检查
     │
  ┌──┴───┐
  ▼      ▼
齐全    缺失
 │       │
 ▼       ▼
继续    澄清HITL
```

**别名处理：**
- LLM 结合上下文判断别名含义
- 置信度高（>= 0.8）→ 直接使用，在日志中记录别名映射
- 置信度低（< 0.8）→ 触发澄清，列出可能的含义供用户选择

**能力校验不通过：**
- 走 HITL 澄清
- 展示"不支持 XXX" + 支持的选项列表
- 用户选择后继续流程

### 4.5 上下文继承规则

多轮对话中，以下字段继承上一轮的值：
- `advertiser_ids`（广告主）
- `time_range`（时间范围）
- `ad_level`（广告层级）

不继承，每轮重新解析：
- `metrics`（指标）
- `group_by`（维度）
- `filters`（过滤条件）

继承策略：如果当前轮用户明确说了新值，用新值；没说但上一轮有，继承上一轮的值。

### 4.6 广告主处理

广告主提取和校验放在第二层报表意图识别中完成：

1. 从用户输入中提取广告主名称 / ID
2. 调用 `advertiser_service` 查询匹配的广告主
3. 匹配失败 → 触发澄清（"未找到匹配的广告主，请重新提供"）
4. 多个匹配 → 触发澄清（列出候选让用户选）

## 5. Layer 2-知识：知识问答意图识别与填充

### 5.1 职责

对知识类问题做结构化理解，判断是否在知识库覆盖范围内，必要时澄清或引导。

### 5.2 提取字段

| 字段 | 说明 | 可选值 |
|------|------|--------|
| `question_type` | 问题类型 | `concept`（概念解释）/ `metric`（指标解读）/ `strategy`（优化策略）/ `operation`（操作指南）/ `troubleshooting`（故障排查） |
| `core_topics` | 核心主题词列表 | `["CTR", "冷启动", "素材优化"]` |
| `knowledge_confidence` | 知识库匹配置信度 | `0.0 ~ 1.0` |
| `query_rewrite` | 检索用查询改写 | 字符串 |

### 5.3 知识库范围匹配

基于 4 大类 25 篇文档的覆盖范围做匹配判断：

| 分类 | 涵盖范围 |
|------|---------|
| 基础概念 | 广告主/计划/组/创意、曝光/CTR、出价方式、定向、落地页 |
| 核心指标 | CPA/CPC/CPM、ROI、归因、ARPU、转化漏斗、留存/LTV |
| 优化策略 | A/B测试、定向调优、素材优化、冷启动、预算出价、问题排查、素材衰退 |
| 系统操作 | 平台操作、报表解读 |

匹配逻辑（LLM 判断）：
- 高置信度在范围内 → 直接走 RAG
- 低置信度 / 边界模糊 → 第一次触发范围引导
- 用户继续问不相关的 → 拒绝回答

### 5.4 范围引导（第一次不匹配时）

向用户展示系统能回答的范围：

> 抱歉，这个问题超出了我的知识范围。我可以回答以下方面的广告相关问题：
>
> - **基础概念**：比如"什么是 CTR？"、"OCPC 是什么？"
> - **核心指标**：比如"ROI 怎么算？"、"归因模型有哪些？"
> - **优化策略**：比如"怎么提高点击率？"、"冷启动跑不动怎么办？"
> - **系统操作**：比如"怎么看报表？"、"A/B 测试怎么做？"
>
> 请在以上范围内提问～

### 5.5 问题澄清

问题太宽泛（如"怎么优化广告"）时，触发澄清：

> 你想了解哪个方面的优化？是素材、定向、出价还是其他？

## 6. 通用澄清机制（HITL）

### 6.1 澄清类型

| 类型 | 触发场景 | 示例问题 |
|------|---------|---------|
| `intent_confirm` | 顶层分类置信度低 | "你是想查询报表数据，还是了解广告知识？" |
| `missing_advertiser` | 报表缺广告主 | "请问你想查看哪个广告主的数据？" |
| `missing_time_range` | 报表缺时间范围 | "请问你想查看哪段时间的数据？" |
| `missing_metrics` | 报表缺指标 | "请问你关注哪些指标？" |
| `missing_ad_level` | 报表缺广告层级 | "请问你想看哪个层级的数据？计划、广告组还是素材？" |
| `unsupported_metric` | 指标不支持 | "抱歉，暂不支持 XXX 指标。支持的指标有：曝光、点击、消耗..." |
| `unsupported_dimension` | 维度不支持 | 类似指标 |
| `alias_confirm` | 别名有歧义 | "你说的'成本'是指总消耗、CPC 还是 CPA？" |
| `knowledge_scope_guide` | 知识问答范围引导 | 展示可回答的 4 大分类 |
| `knowledge_clarify` | 知识问题太宽泛 | "你想了解哪个方面的优化？" |

### 6.2 实现方式

沿用现有 LangGraph interrupt 机制，与当前 `hitl_node` 的方式一致：

1. **Graph 编译时静态声明中断点**：`build_graph()` 中
   `app = graph.compile(interrupt_before=["clarify"])`
2. 各识别节点（intent_classifier / report_intent / knowledge_intent）检测到需要澄清时，
   设置 `state["needs_clarification"] = True` 并将澄清信息写入 `state["clarification"]`
3. Graph 执行到 `clarify` 节点前自动中断（因为 `interrupt_before=["clarify"]`）
4. API 层检测到 interrupt 状态 → 返回 `waiting_for_clarification` 给前端
5. 用户提交澄清 → API 调用 `submit_clarification` → 将用户反馈写入 `user_feedback` → 恢复 graph 执行
6. `clarify` 节点执行：将用户反馈合并到上下文中，路由回对应的识别层重新识别

**clarify 节点的职责**：
- 接收用户反馈
- 检测反馈是否触发意图回退（用户改变了意图类别）
- 路由回对应的识别层重新执行（或回退到第一层）

### 6.3 State 字段

```python
# 澄清相关（扩展现有字段）
clarification: {
    "type": str,               # 澄清类型（见上表）
    "question": str,           # 向用户展示的问题
    "options": list,           # 选项列表（可选，为空则用户自由输入）
    "allow_custom_input": bool,  # 是否允许用户自由输入
}
user_feedback: dict             # 用户的澄清反馈（保持现有字段）
clarification_count: int        # 层内澄清次数（保持现有字段）
```

## 7. 回退与循环机制详解

### 7.1 回退触发条件

只有一种情况触发回退：**第二层澄清时，用户的反馈内容表明意图类别发生了变化。**

示例：
- 第一层分类为 `knowledge`，第二层知识模块发起澄清
- 用户回复："不是，我想查消耗数据"
- 检测到意图变为 `report` → 回退到第一层重新分类

### 7.2 回退检测方式

第二层收到用户澄清反馈后，先做一次轻量的意图判断：
- 如果反馈内容明确指向另一类 → 触发回退
- 如果反馈内容是对当前层的补充 → 正常继续当前层

### 7.3 回退计数与重置

- `reentry_count` 记录回退次数，初始为 0
- 每次回退到第一层，`reentry_count += 1`
- `reentry_count >= 3` → 触发全量重置
- 全量重置：清空所有意图相关 state，返回提示"我们重新开始吧，请描述你的问题"

## 8. 拒答节点（reject_node）

### 8.1 触发场景

1. 顶层分类器高置信度判断为 `out_of_domain`
2. 知识问答第二次仍问不相关问题

### 8.2 拒答话术

**场景 1：顶层直接拒答**
> 抱歉，我只能回答广告相关的问题（包括广告数据查询和广告知识问答）。其他领域的问题我暂时回答不了。

**场景 2：知识问答范围外二次拒答**
> 抱歉，这个问题我回答不了。请在广告相关的范围内提问。

## 9. LLM 调用与容错

### 9.1 LLM 配置

- 使用现有配置的火山引擎 Ark 模型（`ARK_LLM_MODEL`）
- `temperature=0`（分类和结构化提取需要确定性输出）
- 复用现有 `_get_llm()` 单例

### 9.2 重试策略

- 首次调用失败 → 自动重试，共 3 次机会（首次 + 2 次重试）
- 重试间隔：指数退避（1s → 2s）
- 3 次都失败 → 返回服务异常提示

**异常提示话术：**
> 抱歉，当前服务暂时不可用，请稍后再试。

### 9.3 降级策略

LLM 完全不可用时：
- 顶层分类：回退到纯关键词规则（报表关键词 → report，其他 → knowledge）
- 第二层报表：回退到现有纯规则 NLU
- 第二层知识：直接走 RAG（跳过结构化）

降级时记录 warning 日志。

## 10. Graph 流程变更

### 10.1 新的节点清单

| 节点名 | 说明 | 对应旧节点 |
|--------|------|-----------|
| `intent_classifier` | 顶层意图分类器（规则 + LLM） | 替换 `intent_router` |
| `report_intent` | 报表意图识别与填充 | 替换 `nlu` + 部分 `advertiser_handle` |
| `knowledge_intent` | 知识问答意图识别 | 新增 |
| `clarify` | 通用澄清节点 | 替换/增强 `hitl` |
| `reject` | 拒答节点 | 新增 |
| `rag_retrieve` | RAG 检索 | 保持不变 |
| `rag_generate_answer` | RAG 回答生成 | 保持不变 |
| `planner` | 查询规划 | 保持不变 |
| ...其余节点 | 数据/洞察/分析/报告 | 保持不变 |

### 10.2 流程图

```
                    │ (顶层分类 + 置信度) │
                    └─────────┬──────────┘

              ▼               ▼               ▼
       ┌───────────┐   ┌──────────────┐  ┌────────┐
       │ report    │   │ knowledge    │  │ reject │
       │ intent    │   │ intent       │  │  (结束)│
       │ (报表识别) │   │ (知识识别)    │  └────────┘

       │         ▼        │         ▼
       │     clarify      │     clarify/guide
       │         │        │         │

       │   是 → 回退      │         │

                 │        │         │

                     （意图变化时回退到顶层）
```

### 10.3 路由函数

`route_after_classify`（顶层分类后路由）：
- `report` → `report_intent`
- `knowledge` → `knowledge_intent`
- `out_of_domain` → `reject`
- 低置信度 → `clarify`（类型：`intent_confirm`）

`route_after_report_intent`（报表意图后路由）：
- 信息齐全 + 能力校验通过 → `planner`
- 缺信息 / 不支持 / 别名歧义 → `clarify`
- 广告主相关 → （合并到通用澄清）

`route_after_knowledge_intent`（知识意图后路由）：
- 高置信度在范围内 → `rag_retrieve`
- 第一次范围外 → `clarify`（类型：`knowledge_scope_guide`）
- 第二次仍不相关 → `reject`
- 问题太宽泛 → `clarify`（类型：`knowledge_clarify`）

## 11. 状态设计（State 变更）

### 11.1 新增字段

```python
# 顶层分类结果
intent_category: Optional[str]        # report / knowledge / out_of_domain
intent_confidence: float              # 0.0 ~ 1.0
intent_classify_source: str           # rule_fastpath / llm
intent_reason: str                    # 判断依据

# 回退计数
reentry_count: int                    # 回退次数，默认 0

# 澄清信息（结构化，替代原 ambiguity）
clarification: Optional[dict]         # {type, question, options, allow_custom_input}

# 知识问答意图
knowledge_intent: Optional[dict]      # {question_type, core_topics, query_rewrite, confidence}

# 报表意图（扩展原 query_intent）
# 原 query_intent 保留，新增：
# query_intent["ad_level"]: str
# query_intent["top_n"]: int
# query_intent["chart_type"]: str
```

### 11.2 调整字段

- `query_type` → 废弃，改用 `intent_category`
- `ambiguity` → 废弃，改用 `clarification`（结构更丰富）

## 13. 测试策略

### 13.1 单元测试

- **顶层分类器测试**：
  - 规则快筛命中/未命中场景
  - LLM 三分类的各种边界 case
  - 置信度阈值判断
  - LLM 重试与降级

- **报表意图识别测试**：
  - 各字段提取准确率
  - 必填字段缺失澄清
  - 别名歧义处理
  - 能力校验不支持场景
  - 上下文继承

- **知识意图识别测试**：
  - 问题分类准确率
  - 范围匹配判断
  - 范围引导话术

- **回退机制测试**：
  - 回退触发逻辑
  - 回退计数
  - 3 次超限重置

### 13.2 集成测试

- 完整链路：用户输入 → 分类 → 第二层识别 → 下游流程
- 澄清链路：识别 → 澄清 → 用户反馈 → 继续/回退
- 拒答链路：领域外 → 拒答

### 13.3 测试用例覆盖

| 分类 | 用例示例 | 预期 |
|------|---------|------|

## 14. 风险与注意事项

1. **LLM 成本与延迟**：每次对话可能触发 1-2 次 LLM 调用（顶层 + 第二层），需关注成本和响应时间。规则快筛可以覆盖大部分报表查询，降低 LLM 调用率。

2. **澄清轮次过多**：如果必填字段都缺失，可能需要多轮澄清才能收集齐，影响用户体验。可以考虑合并澄清问题（比如一次问多个缺失字段）。

3. **回退误判**：第二层澄清时误判用户意图变化，导致不必要的回退。需要确保回退检测的准确性。

4. **状态管理复杂度**：分层 + 回退 + 多种澄清类型，state 管理会比之前复杂，需要清晰的状态机设计。

5. **现有流程兼容**：需确保现有报表查询和 RAG 流程的接口兼容，平滑过渡。

## 15. 实施建议（分阶段）

建议分两期实施：

**Phase 1：核心能力**
- 顶层意图分类器（规则快筛 + LLM 三分类 + 置信度）
- 拒答节点
- 报表意图识别（LLM 结构化提取 + 必填字段澄清 + 能力校验）
- 通用澄清机制（替代现有 hitl）
- 回退机制

**Phase 2：知识问答增强 + 优化**
- 知识问答意图识别（分类 + 主题提取）
- 知识范围引导
- 上下文继承优化
- 性能优化（提示词精简、缓存）
