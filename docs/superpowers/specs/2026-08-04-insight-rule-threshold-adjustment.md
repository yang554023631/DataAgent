# 洞察规则阈值调整与优化

**日期**: 2026-08-04
**状态**: 已实施
**分支**: `adjust-insight-rules`

## 背景

洞察规则引擎上线后，基于 ES 中 10 个广告主的真实数据验证，发现多条规则命中率为 0。经分析，主要原因是：
1. 阈值设置过高/过低，与实际数据分布不匹配
2. 部分规则只能在有 `ad_group_id` 的上下文中触发，覆盖场景有限
3. 个别规则（如 A06）的数据基础不存在

本次调整的目标：
- 让每条规则在合适的场景下都能触发
- 命中率控制在合理范围（亮点/问题各 15%~30% 的对象命中）
- 保证规则的业务含义仍然成立

## 技术改造

### 批量查询机制

新增了两类批量查询函数，将 N 个对象 × M 条规则的 ES 查询从 O(N×M) 降到 O(1~N/batch)：

**日数据批量查询**：
- `_batch_query_daily_metrics(ids, id_field, batch_size=30)` — 批量查多个对象的日消耗数据
- `_get_daily_data_from_cache()` — 公共缓存函数，供所有需要日数据的规则复用

**受众维度批量查询**：
- `_batch_query_audience_metrics(ids, id_field, audience_type, batch_size=30)` — 批量查多个对象的受众维度数据（设备、地域、性别等）
- `_get_audience_data_from_cache()` — 公共缓存函数，供所有需要受众数据的规则复用

**分批策略**：每 30 个 ID 为一批，防止 terms 查询过大。

### 规则判定模式改造

以下规则从"单对象判定"改为"遍历所有对象 + 批量查询 + 逐条判定"模式：

- 日数据类：A04、A05、P02、P04、P06、P09、P10
- 受众数据类：P07、P08、A08

改造后规则可以在 creative / ad_group 维度下正常触发，不再依赖 context 中的 `ad_group_id` / `creative_id`。

## 各规则详细说明

### A04 消耗曲线健康

**调整**：日消耗变化率阈值从 50% 放宽到 100%

**原因**：mock 数据中日消耗波动较大（常见 100%~400% 的跳变），50% 阈值从未命中。调到 100% 后约 21% 的广告组能命中。

**附加改动**：
- 阈值改为从 yaml 配置读取（`special_rules.A04_healthy_spend.change_threshold`），之前是硬编码
- 改造为批量逐条判定模式

### A05 频次控制良好

**调整**：日均频次阈值从 2.0 放宽到 4.0

**原因**：数据中所有广告组的日均频次都在 3.8~4.7 之间，2.0 永远达不到。4.0 对应约 21% 的命中率。

**附加改动**：
- 阈值改为从 yaml 配置读取（`special_rules.A05_frequency_control.max_freq`），之前是硬编码 2.0
- 改造为批量逐条判定模式

### A06 转化节奏理想

**调整**：整条规则删除

**原因**：规则的业务含义是"24小时内转化占比高"，但现有数据结构中没有转化延迟时长数据。代码用"投放首日转化占比"来近似，逻辑完全不对——衡量的是广告生命周期长短，不是用户决策速度。

**后续**：如果以后有转化延迟时间数据，可重新设计并加回。

### A08 分设备CPA反差亮点

**调整**：cpa_ratio_threshold 从 0.5 放宽到 0.9

**原因**：设备间 CPA 差异普遍在 5%~30%，50% 的反差要求太高。90%（便宜 10% 以上）对应约 17% 的命中率。

**附加改动**：改造为批量逐条判定模式（共用设备受众缓存）

### P02 创意疲劳衰减

**调整**：阈值不变（连续下降 3 天 + 降幅 > 20%）

**原因**：阈值本身是合理的，之前命中少是因为只能在按天分组的查询中触发。改造为批量逐条判断后，命中数正常化。

**附加改动**：改造为批量逐条判定模式

### P04 频次失控

**调整**：阈值从 5.0 收紧到 4.5

**原因**：数据中大部分广告组日均频次在 4.0 左右，5.0 基本触发不了。4.5 能发现频次偏高的对象。

**附加改动**：改造为批量逐条判定模式

### P06 出价策略异常

**调整**：实际生效阈值为 yaml 中的 2.0（200%）

**原因**：代码和配置不一致（代码默认 5.0，yaml 是 2.0）。改造后以 yaml 为准。200% 的单日 CPC 涨幅是合理的异常检测阈值。

**附加改动**：改造为批量逐条判定模式

### P07 地域投放过于集中

**调整**：
- reach_threshold：0.8 → 0.11（单地域占比 > 11%）
- cpa_ratio_threshold：1.5 → 1.2（CPA 是其他均值的 1.2 倍以上）

**原因**：数据中地域分布非常均匀（20 个城市，最高占比仅 10%~20%），80% 的阈值永远触发不了。调到 11% 后命中率约 15%。

**注意**：11% 的"过于集中"在全国性投放场景下语义偏弱，更准确的描述是"头部地域成本偏高"。如果有地域性广告主的数据，可适当上调此阈值。

**附加改动**：改造为批量逐条判定模式

### P08 设备兼容问题

**调整**：ctr_ratio_threshold 从 5.0 降到 1.33（即最差 CTR < 最好的 1/1.33 ≈ 75%，差异 > 25%）

**原因**：设备间 CTR 差异最大约 34%，5 倍差距不可能达到。25% 差异是一个比较合理的"设备表现明显不一致"的阈值。

**附加改动**：改造为批量逐条判定模式

### P09 竞品活动冲击

**调整**：阈值不变（CPC 涨 > 80% + CTR 跌 > 40%）

**原因**：阈值本身合理，之前命中 0 是因为只能单对象判断。批量改造后正常触发。

**附加改动**：改造为批量逐条判定模式

### P10 消耗波动异常

**调整**：实际生效阈值为 yaml 中的 2.0（200%）

**原因**：代码和配置不一致（代码默认 5.0，yaml 是 2.0）。改造后以 yaml 为准。200% 的单日消耗波动作为异常检测阈值合理。

**附加改动**：改造为批量逐条判定模式
